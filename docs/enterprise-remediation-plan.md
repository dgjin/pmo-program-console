# PMO 项目群管理台企业级投产整改实施计划

编制日期：2026-11-04  
基线版本：v1.38.0  
依据：[企业级投产评审](enterprise-readiness-review.md)  
目标：12 周内关闭 P0 阻断项，完成试点验证和企业级投产评审；P1/P2 在投产后 90–180 天推进。

## 一、总体策略

### 1.1 两条线并行

- **整改线**：按 P0 清单补身份、边界、数据库、灾备、可观测性、安全、发布和内控。
- **试点线**：第 4 周起开 2–3 个项目、10–20 人试点，边用边验证；试点不等于企业级投产。

### 1.2 不做什么

这 12 周不做下面这些，避免范围失控：

- 不拆微服务。
- 不做多租户。
- 不做移动端原生 App。
- 不做完整财务/采购 ERP。
- 不做电子签章。
- 不做会议周期预订、用品采购单等扩展功能。
- 不在 P0 阶段强行迁 PostgreSQL；先设迁移触发条件，达到再启动。

### 1.3 核心原则

1. **先保命，再提效**：备份恢复、身份、TLS 优先于新功能。
2. **能自动检查的，不靠人记**：迁移、备份、探活、安全、回滚都要有脚本或流水线。
3. **每个 P0 有验收证据**：截图、命令输出、演练记录、测试报告，不接受“已经改了”。
4. **变更冻结**：整改期间只接受 P0 修复和安全补丁，新功能排到投产后。
5. **单实例优先**：当前是模块化单体 + SQLite，先按单实例做稳；HA 和 PostgreSQL 作为 P1 决策。

## 二、目标与验收口径

### 2.1 企业级投产目标

| 指标 | 目标 |
| --- | --- |
| 身份 | 生产用户 100% SSO，管理员 100% MFA |
| 边界 | 外网只开 443，5177 不可达；HSTS、Secure Cookie 生效 |
| 可用性 | 工作时间 ≥ 99.5%；发布/重启无 5xx |
| 性能 | 真实数据、50 并发下 p95 < 500ms |
| 灾备 | 每日自动备份成功 100%；恢复演练 RTO ≤ 2h |
| 数据 | 关键表有外键；迁移可重复；无孤儿数据 |
| 安全 | 第三方渗透无高危/中危，或有明确修复计划 |
| 审计 | 关键操作可追溯，保留 ≥ 1 年，不可普通管理员删除 |
| 发布 | staging 升级/回滚通过；有制品哈希和回滚点 |
| AI | 敏感项目禁外部模型；有预算、脱敏、抽检 |

### 2.2 Go/No-Go 门槛

**企业级 Go 必须全部满足：**

- P0 清单 100% 关闭，验收证据齐全。
- 试点运行 4 周，无 P0/P1 数据或安全事件。
- 第三方渗透测试完成，高危/中危清零或有签字豁免。
- 真实数据压测达标。
- 业务 UAT 签字，培训完成。
- 回滚演练通过，上一版包和数据库备份可用。
- 运维值班、告警接收人、支持群明确。

**出现任意一条即 No-Go：**

- 没有 SSO/MFA，或管理员账号共用。
- 没有可恢复的备份，或未做恢复演练。
- 数据库无外键、无版本化迁移、`busy_timeout=0`。
- 没有监控告警。
- 高危漏洞未修复。
- 审批人可以审批自己的申请且无补偿控制。
- 敏感项目仍走外部 AI。

## 六、周计划（可执行版）

### W0：启动与冻结

- 确认范围、预算、人员、IdP/证书/备份存储/渗透厂商。
- 建 staging，冻结新功能。
- 输出 P0 燃尽表和风险清单。
- **Gate**：计划签字，资源到位。

### W1：TLS 与 SSO 设计

- Nginx TLS、5177 收口、VPN/白名单。
- OIDC 应用注册、角色映射表。
- 备份存储和密钥管理方案。
- **Gate**：外网不可达 5177，SSO 测试登录成功。

### W2：身份与会话

- SSO 上线测试环境，MFA 管理员。
- 会话空闲/绝对超时、单点登出。
- 密码重置改造、弱密码策略。
- **Gate**：M1 安全边界可用。

### W3：数据库迁移准备

- `busy_timeout`、外键迁移脚本、迁移框架。
- 在数据库副本上跑迁移和回滚。
- 自动备份、`.ai-key` 备份。
- **Gate**：迁移演练通过。

### W4：恢复演练与试点启动

- 临时环境恢复数据库 + Key，验证核心页面。
- 2–3 个项目、10–20 人试点。
- 签署试点范围和例外清单。
- **Gate**：M2 可恢复、可迁移；试点 Gate。

### W5：可观测性

- `/ready`、请求 ID、结构化日志。
- 指标、仪表盘、告警接收人。
- 优雅停机、超时。
- **Gate**：能定位一次模拟 500。

### W6：安全硬化

- CSRF/Origin 严格、全局限流。
- 容器非 root、只读、镜像扫描。
- 审计只追加。
- **Gate**：M3 出问题能发现。

### W7：staging 与发布

- staging 部署、迁移测试、回滚演练。
- CI 覆盖率、SBOM、镜像扫描。
- 变更单模板。
- **Gate**：staging 升级/回滚通过。

### W8：内控与权限

- 审批人分离、代理审批、PMO 自批例外。
- 角色细化、权限矩阵测试。
- 审计保留和导出。
- **Gate**：M4 可发布、可追责；启动渗透测试。

### W9：测试与压测

- E2E 主链路、会议/用品链路。
- 真实数据压测。
- 渗透测试执行。
- **Gate**：测试报告、渗透初报。

### W10：修复与 UAT

- 渗透问题修复、复测。
- 性能调优。
- UAT、培训、支持手册。
- **Gate**：M5/M6 业务验收。

### W11：上线演练

- 备份 → 迁移 → 部署 → 冒烟 → 回滚全流程。
- 确认上一版包、数据库备份、Key、证书。
- **Gate**：演练通过，Go/No-Go 预审。

- 观察 30 分钟，开 hypercare。
- **Gate**：正式 Go。

## 七、上线切换与回滚

### 7.1 切换步骤

1. 提前 7 天完成备份恢复演练和回滚演练。
2. T-1 冻结数据变更，通知用户。
3. T0 停应用，做一次完整备份（DB + `.ai-key` + 配置）。
4. 执行迁移，记录版本和耗时。
5. 部署新包，启动，检查 `/ready`。
6. 冒烟：PMO 登录、项目、计划、周报、审核、会议、用品、AI。
7. 开放用户，观察 30 分钟。
8. 记录发布证据，关闭变更单。

### 7.2 回滚触发

- 登录不可用超过 5 分钟。
- 关键页面持续 500 或错误率 > 1%。
- 数据错乱、丢记录。
- 安全事件。
- 备份/迁移失败且短时间修不好。

### 7.3 回滚步骤

停服务 → 恢复上一版数据库备份 → 恢复 `.ai-key` → 切回上一版包 → 启动 → 验证登录和核心页面 → 通知用户。

## 十、PostgreSQL 迁移决策

**P0 阶段不迁移**，保持单实例 SQLite。W8 做一次决策评审，出现任意两条再启动迁移：

- 需要多实例/HA。
- 并发活跃用户 > 50 或持续写入 > 20 次/分钟。
- 数据库 > 2GB，备份窗口 > 30 分钟。
- 需要只读副本/报表库/实时集成。
- 真实数据 p95 持续 > 500ms，优化后仍不达标。

迁移按“双写/同步 → 校验 → 切读 → 切写 → 回滚窗口”推进，不在 P0 期间做。

| 风险 | 概率 | 影响 | 应对 |

| 真实数据压测不达标 | 中 | 中 | 索引/查询优化；必要时提前评估 PostgreSQL |
| 试点用户不买账 | 中 | 中 | PMO 牵头、培训、周报自动带入、试点 Champion |
| 范围蔓延（新功能） | 高 | 中 | 变更冻结，新需求排 P1 |

## 十三、预算与资源粗估

### 人力

- 开发/架构：12 周 × 1.0 = 60 人日。
- DevOps：12 周 × 0.5 = 30 人日。
- 安全：8 周 × 0.25 = 10 人日。
- QA：8 周 × 0.5 = 20 人日。
- PMO/UAT：12 周 × 0.5 = 30 人日。
- 支持：投产后 2 周 × 0.3 = 3 人日。

合计约 **150–170 人日**，不含渗透厂商和基础设施费用。

### 基础设施

- 试点：2 vCPU / 4GB 单实例 + Nginx + 备份存储 + 监控。
- 企业：4 vCPU / 8GB，反代/网关、日志、监控、对象存储备份；如 HA，另算 PostgreSQL/多实例。
- 渗透测试：按厂商报价，预留 2 周修复窗口。
- AI：按月 token 预算，先内网模型，外部模型只对非敏感项目开放。

## 十六、结论

这份计划的核心不是“再加几个功能”，而是把当前这套**部门级可用的 PMO 工具**，按企业生产系统的标准补齐身份、边界、数据、灾备、可观测性、发布和内控。

如果资源和外部依赖按时到位，**12 周可以达到企业级投产门槛**；如果 SSO、渗透或备份恢复任何一项拖延，宁可顺延，也不要用“试点能用”去替代“生产可管”。
