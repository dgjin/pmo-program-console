# PMO 项目群管理台企业级投产评审

评审日期：2026-11-04  
评审版本：v1.38.0  
评审角色：项目管理 + 应用架构/开发  
评审方式：代码与配置走查、数据库检查、测试与脚本复核、部署文档审阅；未做第三方渗透测试、未做真实生产压测。

## 一、结论

**不建议按企业级全量投产标准直接上线。**

当前版本适合作为**部门级/项目群级试点**：2–3 个项目、10–20 个用户、内网或 VPN 访问、PMO 全程盯、每日备份可恢复。要达到企业级生产标准，还需要补身份、灾备、可观测性、数据库约束、发布治理和安全测试，预计 8–12 周。

企业级投产综合评分：**2.8 / 5**。  
功能适配度明显高于工程成熟度，主要风险不在“功能有没有”，而在“出了事能不能发现、能不能恢复、能不能追责”。

## 三、当前做得好的地方

这些不是客套，是继续演进的基础：

- **零运行时依赖**：没有 npm 依赖，供应链攻击面小，部署简单。
- **测试不是零**：46 项 API 集成测试，覆盖认证、权限、多项目群、计划、周报、EVM、验收、变更、会议、用品等核心流程。
- **CI 有基础**：接口、浏览器冒烟、安全基线、轻量压测都在跑。
- **安全基线有内容**：CSP、X-Frame-Options、Origin 校验、登录限流、路径穿越、SQL 注入式登录、跨项目越权都做了检查。
- **审计有落点**：关键动作写审计日志，能查操作人、对象、项目和时间。
- **文档比较完整**：README、部署说明、实施计划、上线建议、独立评估都在仓库里。
- **业务深度够**：不是只有 CRUD，计划调度、基线偏差、EVM、关口清单、周报审核、知识库、AI 引用都做进去了。

## 四、企业级 P0 阻断项

下面任何一项不关闭，不建议宣布企业级投产。

### P0-1 身份与访问：没有 SSO/MFA

**现状**

- 本地账号 + scrypt 密码；密码最短 8 位，无复杂度/泄露密码检查。
- 会话固定 7 天，没有空闲超时、没有主动轮换。
- 没有 SSO/OIDC/LDAP，没有 MFA。
- PMO 可重置密码，接口会把新密码明文返回给管理员。
- 会议、用品由 PMO 单级审批，PMO 自己的申请自动通过，审批控制形同虚设。

**风险**

- 账号共享、弱密码、离职账号未及时停用。
- 管理员账号一旦泄露，等于全部项目数据泄露。
- 自己申请自己批，内控和审计过不了。

**建议**

1. 接企业 OIDC/SSO（Azure AD、Keycloak、企业微信/钉钉扫码均可），本地账号只保留应急管理员。
2. 管理员和高权限角色强制 MFA。
3. 会话改为“空闲 2 小时 + 绝对 8 小时”，支持单点登出和会话列表。
4. 密码重置改成一次性链接/临时密码，接口不回显明文。
5. 会议、用品、变更、验收增加双人复核或至少“申请人 ≠ 审批人”；PMO 自批要有书面例外和审计标记。
6. 角色从“PMO/乙方 PM/甲方 PM”细化到“系统管理员、PMO、项目负责人、审批人、只读”，并支持按项目授权。

**验收**

- 100% 生产用户走 SSO，MFA 覆盖率 100%。
- 离职/停用账号 10 分钟内失效。
- 审批记录能证明申请人与审批人不同，或有明确例外标识。
- 密码重置响应中不出现明文密码。

### P0-2 传输与边界：不能直接暴露 5177

**现状**

- 应用本身不终止 TLS；Docker Compose 直接映射 `5177:5177`，默认监听 `0.0.0.0`。
- 代码支持 `X-Forwarded-Proto: https` 下的 Secure Cookie/HSTS，但依赖外部反代正确配置。
- 没有 WAF、IP 白名单、VPN 接入说明的强制约束。

**风险**

- 直接暴露时 Cookie 不带 Secure，流量明文。
- 反代配错会导致 Secure/HSTS 失效，但应用不会报警。

**建议**

1. Nginx/Traefik/云 LB 终止 TLS，应用只监听 `127.0.0.1:5177` 或容器内网。
2. 强制 HTTP → HTTPS，HSTS `max-age=31536000; includeSubDomains`。
3. 公网不开放；至少 VPN/零信任网关 + IP 白名单。
4. 增加部署后自检：`curl -I` 验证 HSTS、Secure Cookie、HTTP 跳转。
5. 证书自动续期和到期告警。

**验收**

- 外网只能访问 443，5177 不可达。
- 登录响应 Cookie 带 `Secure; HttpOnly; SameSite=Lax`。
- HSTS 生效，HTTP 自动跳转。

### P0-3 数据库：没有外键、没有迁移、没有 busy timeout

**现状**

- 39 张表、21 个索引，**0 个 FOREIGN KEY 定义**；`PRAGMA foreign_keys` 为 1，但没有约束可执行。
- `PRAGMA busy_timeout` 为 **0**。
- `PRAGMA user_version = 20` 是启动时直接写的，没有版本化迁移脚本；只有少量 `ensureColumn` 补列。
- 单文件 SQLite，WAL 模式；当前 384 KB、4 个项目、6 个用户、130 条审计。

**风险**

- 删除项目/用户/房间后出现孤儿记录；靠应用层检查，漏一处就脏数据。
- 备份、VACUUM、外部查询与写入并发时容易 `database is locked`。
- 升级时表结构变更不可重复、不可回滚；多环境漂移。
- 数据量上来后单文件备份窗口、恢复时间不可控。

**建议**

1. 设置 `PRAGMA busy_timeout = 5000`，`synchronous = NORMAL`，定期 `wal_checkpoint(TRUNCATE)`。
2. 增加真实外键；SQLite 不能直接给已有表加 FK，需要“新表 + 数据迁移 + 重命名”的一次性迁移。
3. 建立 `migrations/` 版本化 SQL，按 `user_version` 逐版执行，迁移前自动备份，失败回滚。
4. 启动时做 `PRAGMA integrity_check`（或每日任务），异常告警。
5. 对项目、用户、房间、物品删除做引用检查，禁止物理删除有历史的对象。

**验收**

- 关键表有 FK，删除被引用对象返回明确错误。
- 迁移可在空库和旧库上重复执行，失败可回滚。
- 并发压测无 `SQLITE_BUSY`。
- 迁移前后 `integrity_check` 为 ok。

### P0-4 灾备：备份只有脚本，没有体系

**现状**

- `scripts/backup.js` 用 `VACUUM INTO` 生成一致性快照，方向正确。
- 当前 `backups/` 只有一份 2026-11-03 的 156 KB 备份。
- 没有定时调度、异地副本、加密、保留策略、恢复脚本和恢复演练记录。
- `data/.ai-key` 不在备份脚本里；只恢复数据库会导致 AI Key 解不开。
- 没有明确 RPO/RTO。

**风险**

- 磁盘损坏/误删 = 数据全丢。
- 备份和数据库同盘，一起坏。
- 恢复时发现 Key 丢了、版本不匹配、迁移失败。

**建议**

1. 每日自动备份，至少保留 30 天日备 + 12 个月月备。
2. 备份异机/对象存储，传输和静态加密；备份文件校验 SHA-256。
3. 同时备份 `data/.ai-key`（或使用 `PMO_CONFIG_SECRET` 并纳入密钥管理），否则 AI 配置不可恢复。
4. 写恢复脚本：停服 → 恢复 DB → 恢复 Key → 启动 → 冒烟 → 记录耗时。
5. 每季度恢复演练，目标：试点 RPO ≤ 24h、RTO ≤ 2h；企业级 RPO ≤ 15min 需要 WAL 归档或 PostgreSQL。
6. 备份失败告警，连续两次失败升级。

**验收**

- 自动备份连续 7 天成功。
- 从备份恢复到临时环境，登录、项目、周报、会议、用品都正常。
- 恢复演练有记录、有耗时、有签字。

### P0-5 可观测性：出事只能靠用户报错

**现状**

- 日志只有 `console.log/error`，没有请求 ID、结构化字段、慢请求、错误分类。
- `/api/health` 返回 `{ok, db: DB_FILE, today}`，暴露数据库路径，且不检查数据库可读。
- 没有 `/ready`、没有指标端点、没有告警、没有日志轮转。
- 没有 `SIGTERM/SIGINT` 优雅停机；进程被杀时可能有未完成写入。

**风险**

- 无法回答“过去一小时有多少 500”“哪个接口慢”“谁在什么时候被拒绝”。
- 容器重启/滚动发布时连接被硬断。
- 磁盘满、备份失败、DB 损坏不能提前发现。

**建议**

1. `/api/health` 只返回 `{ok:true}`；新增 `/api/ready` 做 `SELECT 1` 和迁移状态检查。
2. 引入请求 ID、结构化 JSON 日志、耗时、状态码、用户 ID（脱敏）。
3. 增加 Prometheus 指标或至少定期落库/日志统计：请求数、错误率、p95、DB 大小、备份状态、登录失败。
4. 外部探活每 5 分钟；磁盘、进程、备份、证书、错误率告警。
5. 加 `SIGTERM` 处理：停止接收新请求 → 关闭 server → 关闭 DB。
6. 日志轮转和保留 30–90 天。

**验收**

- 能在 5 分钟内定位一次 500 的请求、用户、接口和堆栈。
- 备份失败/磁盘 80%/证书 30 天到期有告警。
- 滚动重启无 5xx。

### P0-6 安全硬化：基线不等于渗透测试

**现状**

- 有 CSP、X-Frame-Options、nosniff、Referrer-Policy、Permissions-Policy、COOP。
- 写操作校验 Origin，但**缺少 Origin 头时放行**；没有 CSRF Token。
- 登录限流按用户名+IP，其他接口没有全局限流。
- Docker 基础镜像默认 root，没有 `USER node`、没有只读文件系统、没有 `init`。
- 没有依赖漏洞扫描（零依赖是优势）、没有 SAST、没有第三方渗透测试。
- 审计日志可被有数据库权限的人修改，没有哈希链/只追加存储。

**建议**

1. 写操作强制要求 Origin 或 CSRF Token；对缺失 Origin 的非浏览器客户端使用 API Token。
2. 全局限流：登录、AI、导入、导出、审批分别限流；按 IP + 用户 + 接口。
3. Docker 使用非 root 用户、`read_only`、`tmpfs`、`init: true`、最小权限。
4. 每次发布跑 Node 版本 CVE 检查、容器镜像扫描、SAST；上线前做第三方渗透测试。
5. 审计日志只追加、定期归档、哈希链或外部 SIEM；保留至少 1 年。
6. 数据库磁盘加密；备份加密；敏感配置进 Secrets Manager，不进仓库。
7. 对导出、批量导入、管理员操作增加二次确认和审计。

**验收**

- 渗透测试无高危/中危，或全部有修复计划。
- 缺失 Origin 的写请求被拒绝。
- 容器以非 root 运行，镜像扫描无高危。
- 审计日志不可被普通管理员删除。

### P0-7 发布治理：没有 staging 和版本化迁移

**现状**

- CI 跑测试、UI 冒烟、安全基线、压测，但没有部署流水线、没有 staging、没有制品签名/SBOM。
- 版本号手工改，迁移靠启动时建表和少量补列。
- 没有发布审批、变更单、回滚脚本演练记录。
- Dockerfile 把 tests/docs 也打进镜像，镜像不够干净。

**建议**

1. 三套环境：dev、staging（接近生产数据规模）、prod。
2. CI 增加：覆盖率门槛（先 60%，逐步 75%）、迁移测试、制品 SHA-256、SBOM、镜像扫描。
3. 发布流程：变更单 → 备份 → 迁移 → 部署 → 冒烟 → 观察 30 分钟 → 关闭变更单。
4. 回滚脚本和上一版镜像/包必须随时可用；数据库迁移必须可逆或前向兼容。
5. 镜像只复制运行所需文件，非 root，固定 Node 22 小版本。

**验收**

- staging 能完整走一遍升级/回滚。
- 每次发布有制品哈希、迁移记录、冒烟结果、回滚点。
- 生产发布不需要手工改服务器文件。

### P0-8 AI 治理：外部模型的数据边界没定

**现状**

- 管理维护可配 DeepSeek/OpenAI 兼容接口，Key 加密保存，前端不回显。
- 项目摘要、风险、周报、知识库片段会发给外部模型。
- 有 1.5 秒/用户限流，但没有 token 预算、成本上限、内容脱敏、模型评测。
- AI 输出只做草稿，不自动写库，这是对的。

**风险**

- 项目名称、风险、周报、合同金额等敏感信息出境/出内网。
- Prompt 注入、模型幻觉、错误建议被当成结论。
- 成本不可控，密钥被滥用。

**建议**

1. 做数据分级：公开/内部/敏感/机密；敏感项目禁用外部模型。
2. 优先内网模型；外部模型必须走企业合规评审、DPA、数据保留条款。
3. 发送前脱敏：人名、手机号、金额、合同号可配置掩码。
4. token 预算和日/月成本上限；超限降级到本地摘要。
5. 建立 20–50 条评测问题，定期抽检；AI 输出保留“草稿”标识和引用。
6. 记录调用日志（不含密钥/敏感原文），支持审计和关闭开关。

**验收**

- 敏感项目无法调用外部模型。
- 月度 token 成本有上限和告警。
- AI 输出抽检有记录，错误率可接受。

## 五、P1：30–90 天应补的能力

1. **可访问性到 WCAG 2.1 AA**：现在只查了标签、alt、重复 ID，缺少键盘全流程、对比度、屏幕阅读器、焦点顺序；建议引入 axe-core（仅测试依赖）并做人工走查。
2. **真实数据压测**：当前 84 请求、4 个项目、p95 10ms，不能代表生产。用 50–100 个项目、1 万任务、1000 周报、50 并发跑，记录 p95、DB 大小、备份窗口、SQLite 锁。
3. **E2E 覆盖核心链路**：建项目 → 计划 → 基线 → 周报 → 审核 → 关口 → 验收 → 归档；会议预订 → 审批 → 取消；用品申请 → 发放 → 库存。
4. **前端可维护性**：`public/app.js` 7436 行、`app.css` 4038 行，建议拆模块/按页面懒加载，至少把路由、组件、API、Markdown、编辑器分开；不一定要上框架，但要降低单文件修改风险。
5. **数据库约束与归档**：外键、软删除、审计归档、历史版本清理策略。
6. **会议/用品内控**：双人审批、代理审批、取消截止时间、重复预订/周期会议、库存盘点和补货申请；别让 PMO 自批成为默认。
7. **权限细化**：按项目群/项目/功能授权，客户端只读，财务字段单独权限；支持权限变更审计。
8. **数据保留与删除**：项目、周报、审计、AI 日志的保留期限；离职/客户退出后的删除流程；个人信息清单。
9. **监控面板**：请求、错误、DB、备份、登录失败、AI 调用、库存低水位。
10. **供应链与许可证**：零依赖是优势，但 Node 版本、Chrome、字体、CDN（如果有）要固定和审查；生成 SBOM。

## 六、P2：90–180 天架构演进

### 不建议现在做微服务

当前是典型的模块化单体，业务边界还在变，拆微服务只会增加部署、事务、排障成本。建议保持**模块化单体 + 单实例**，先把运维和身份补齐。

### PostgreSQL 迁移触发条件

出现下面任意两条，再评估 PostgreSQL：

- 需要多实例/高可用，SQLite 单写入成为硬约束。
- 并发活跃用户 > 50，或持续写入 > 20 次/分钟。
- 数据库 > 2 GB，备份窗口 > 30 分钟。
- 需要报表库/只读副本/跨系统实时集成。
- p95 在真实数据下持续 > 500ms，且优化后仍不达标。

迁移时按“先双写/同步 → 校验 → 切读 → 切写 → 回滚窗口”推进，不要一次性停机割接。

### 功能演进优先级

- **核心 PMO**：组合财务、资源平衡、跨项目依赖、收益实现、变更影响分析。
- **会议**：周期会议、ICS 邀请、时区、设备/座位、取消策略、代理审批。
- **用品**：盘点、补货申请、采购单、成本中心、领用限额、条码。
- **AI**：内网模型、RAG 评测、引用准确性、成本治理、敏感信息脱敏。
- **集成**：企业 SSO、HR 组织架构、财务/采购、邮件/IM 通知。

## 七、上线决策

### 可以试点（Conditional Go）

满足以下条件，可开 2–3 个项目、10–20 人试点：

- TLS + VPN/内网，5177 不直接暴露。
- SSO 或至少强密码 + 管理员 MFA（如果企业已有统一身份，优先接）。
- 每日自动备份、异机保存、恢复演练一次。
- 监控探活、日志有人看、备份失败告警。
- 生产库清空演示数据，真实账号、项目、模板、日历初始化完成。
- PMO 自批有书面例外，会议/用品审批有第二人复核。
- 回滚包、回滚步骤、责任人明确。

### 不建议企业全量（No-Go）

以下任意一项成立，不建议全量：

- 没有 SSO/MFA，管理员账号共用。
- 没有可恢复的备份，或从未演练。
- 数据库无外键、无迁移、无 busy timeout。
- 没有监控告警，出问题只能等用户报。
- 没有第三方渗透测试或高危未修复。
- PMO 可以自己申请自己批，且无补偿控制。
- AI 外部模型处理敏感项目，未做数据分级。

## 八、建议的 8–12 周整改路线

| 周次 | 目标 | 交付物 | 验收 |
| --- | --- | --- | --- |
| 第 1–2 周 | 边界与身份 | Nginx TLS、VPN/IP 白名单、SSO/MFA 方案、会话策略 | 外网不可达 5177，SSO 登录成功 |
| 第 2–3 周 | 灾备 | 定时备份、异机加密、恢复脚本、Key 备份 | 恢复演练 ≤2h，数据完整 |
| 第 3–4 周 | 数据库 | busy_timeout、FK、版本化迁移、integrity_check | 迁移可重复，无孤儿数据 |
| 第 4–5 周 | 可观测性 | 结构化日志、请求 ID、指标、告警、优雅停机 | 5 分钟内定位 500，重启无 5xx |
| 第 5–6 周 | 安全硬化 | 非 root 容器、CSRF/Origin 策略、全局限流、渗透测试 | 无高危，缺失 Origin 被拒绝 |
| 第 6–7 周 | 发布治理 | staging、CI 覆盖率、SBOM、回滚演练 | staging 升级/回滚通过 |
| 第 7–8 周 | 内控 | 审批人分离、代理审批、审计只追加 | 申请人≠审批人 |
| 第 8–9 周 | 真实压测 | 50–100 项目、50 并发、备份窗口 | p95 <500ms，锁等待可接受 |
| 第 9–10 周 | AI 治理 | 数据分级、脱敏、预算、评测 | 敏感项目禁外部模型 |
| 第 10–12 周 | UAT 与上线 | 用户培训、支持群、变更单、Go/No-Go | 业务签字，无 P0 阻断 |

## 九、团队与成本粗估

- **开发/架构**：1 人，8–12 周，负责 SSO、迁移、可观测性、安全修复。
- **运维**：0.5 人，负责 TLS、容器、备份、监控、发布。
- **安全**：0.2–0.3 人，负责渗透测试、数据分级、AI 合规。
- **PMO 产品负责人**：1 人，负责流程、UAT、培训、数据初始化。
- **一线支持**：1 人，工作时间答疑和问题分流。

基础设施建议：

- 试点：2 vCPU / 4 GB，单实例 + Nginx + 每日备份。
- 企业：4 vCPU / 8 GB，反代/网关、监控、日志、对象存储备份；如果要求 HA，转 PostgreSQL + 多实例。
- AI：按月设 token 预算，先内网模型，外部模型只对非敏感项目开放。

## 十、最值得先做的 10 件事

1. 接 SSO，管理员上 MFA，会话改为空闲 2h/绝对 8h。
2. 把 5177 收到反代后面，强制 HTTPS/HSTS，VPN/白名单。
3. 每日自动备份到异机、加密、保留 30/90 天，做一次恢复演练。
4. 备份 `data/.ai-key`，否则 AI Key 恢复不了。
5. 加 `busy_timeout=5000`、真实外键、版本化迁移。
6. 加 `/ready`、请求 ID、结构化日志、备份/磁盘/错误率告警、优雅停机。
7. 容器非 root、只读文件系统、固定 Node 小版本、镜像扫描。
8. 写操作强制 Origin 或 CSRF Token，全局限流。
9. 会议/用品/变更/验收禁止自批，至少第二人复核。
10. 做一次第三方渗透测试和真实数据压测，再谈全量。

## 十一、一句话总结

这套系统的业务功能已经超过很多内部工具，但企业投产不是“功能演示通过”就结束了。现在的短板是**身份、灾备、可观测性、数据约束和发布治理**；这些补齐之前，最合适的定位是“部门试点”，不是“企业级生产系统”。
