# PMO 项目群管理台独立评估

评估日期：2026-11-03　版本：v1.10　方式：代码与数据模型审阅、页面走查、接口测试复核  
说明：这是外部视角的独立评估，不是项目内自评，也不是安全审计或 PMI 认证。

## 一、结论

**定位判断：作为 1 个 PMO、10–30 名项目经理的内部项目群管理工具，完成度已经不错；作为集团级 PPM / 项目管理平台，还差三层东西：计划数据的真实性、治理动作的闭环、生产环境的就绪度。**

综合评分 **3.1 / 5**。

拆开看：

- 功能覆盖 **3.7**：台账、关口、双 PM、周报计划、PMP 过程、任务级 WBS 都有。
- 管理有效性 **3.0**：计划、周报、EVM 还是三套数，PMO 仍要二次核对。
- 生产就绪 **2.8**：本地账号、无 MFA/SSO、SQLite 单机、备份靠手工 cron、审计无保留策略。

项目内自评是 3.7，偏重“功能有没有”；这份评估更看“管理层能不能拿它做决策”。两者不矛盾，但不是一回事。

## 二、评分

| 维度 | 分数 | 判断 |
| --- | --- | --- |
| 治理与流程 | 3.4 | 阶段关口、章程、变更、经验教训、甲乙双方职责都有；关口条件、决策行动项还没闭环 |
| 计划与执行 | 3.7 | 任务级 WBS、前置排期、基线、关键路径是明显进步；任务、周报、EVM 尚未同源 |
| 组合与收益 | 2.2 | 只有一个项目群，没有收益台账、商业论证、优先级评分、投资决策 |
| 数据与报表 | 3.0 | 报表能自动生成，但没有趋势快照、版本、批注，指标口径也没固化 |
| 安全与运维 | 2.8 | 密码哈希、会话、CSP、审计都有；SSO/MFA、TLS、自动备份、审计保留不足 |
| 体验与采纳 | 3.1 | 信息密度高、页面多，缺全局搜索、通知、移动端快速更新 |
| 工程质量 | 3.3 | 25 项接口测试、零依赖、部署简单；单体文件大、无 CI、无前端/E2E 测试 |
| 扩展性 | 2.8 | 10–50 人够用；多项目群、多实例、后台任务会很快碰到天花板 |

## 三、做得好的地方

1. **数据模型覆盖面广，而且不是摆设。** 22 张表，项目、里程碑、风险、投入、关口、周报、计划、版本、评论、依赖、章程、变更、经验教训、任务计划都有对应结构。多数同类原型只有项目和周报两张表。
2. **双项目经理的权限边界清楚。** 甲方只读可评论、乙方维护、PMO 指定，服务端按项目上的 `vendor_pm_id` / `client_pm_id` 判断，不是前端藏按钮。
3. **任务级计划做到了“能排”。** 工作日排期、FS 前置、阶段汇总、里程碑、基线、关键路径都有，且循环依赖会被服务端拒绝。这在自研 PMO 工具里不常见。
4. **工程约束克制。** 零 npm 依赖、Node 内置 SQLite、无构建步骤，内网解压即跑；对交付和运维是实打实的优势。
5. **测试和文档比一般原型扎实。** 25 项接口测试覆盖认证、权限、双 PM、账号维护、计划、审核、备份恢复；README、DEPLOY、评估记录、预览图齐全。
6. **审计意识在。** 登录、提交、审核、账号维护、计划变更都写审计，密码不落日志。

## 四、关键问题

### 1. 计划、周报、EVM 是三套数（P0）

这是当前最值得先改的问题。

- `plan_tasks.progress` 是任务进度，`projects.progress` 是项目进度，周报里的 `content.progress` 又是第三个数。
- 周报不会从任务计划带出进度，任务进度也不会汇总回项目；PMO 要在三个地方对。
- EVM 的 PV/EV 用的是 `projects.progress` 和项目计划日期，不是任务基线；任务级基线设了，EVM 不认。
- `milestones` 和 `plan_tasks.kind='milestone'` 是两套里程碑，互不同步。
- `computePlan()` 在 GET 请求里回写排期，读接口有副作用，后面做缓存、只读副本、并发时会别扭。

**后果**：甘特图看起来专业，但管理层看到的进度、周报里的进度、EVM 算出来的进度可能不是一回事。时间一长，PMO 会回到 Excel 对账。

**建议**：

- 明确“任务计划是进度唯一源”：任务进度 → 阶段汇总 → 项目进度 → 周报预填 → EVM 的 EV。
- 周报打开时自动带出本周应完成/已完成任务，项目经理只确认，不重复填百分比。
- PV 按基线任务的时间分布计算，不再用项目起止日期拍脑袋。
- 计划里程碑与项目里程碑二选一，或建立明确同步规则（建议计划里程碑为主，项目台账只读汇总）。
- 把 `computePlan()` 从 GET 里拿出来，改成写操作后重算，或提供显式的“重算”命令。

### 2. 收益与组合管理缺失（P0/P1）

P3O / MoP 的核心不是“项目跟得细”，而是“为什么做这个项目、做完得到了什么”。

现在没有：

- 收益台账：收益基线、目标值、当前值、责任人、实现时间。
- 商业论证/立项理由：只靠章程里的目的和目标，不能比较。
- 组合优先级：战略契合、收益、风险、投入没有评分，项目堆在一起。
- 多项目群：`programs` 只有一行，`buildModel()` 默认取第一个项目群。
- 投资/预算阶段释放：关口通过不自动影响预算。

**建议**：先做一张 `benefits` 表和一张组合优先级评分表，不要急着做复杂组合优化。能回答“这 9 个项目按收益/风险/投入排序，钱应该先给谁”就已经有用。

### 3. 变更、关口、客户验收没有真正闭环（P1）

- 变更审批通过后，不会更新预算、计划日期或任务基线；审批结论和项目数据是分开的。
- 关口“有条件通过”的条件没有变成行动项，没人跟踪关闭。
- 甲方项目经理只能看和留言，没有正式的验收/确认记录。
- 风险应对措施没有落到任务或行动项，风险关闭靠手改状态。

**建议**：

- 增加 `actions` 表：来源（关口/变更/风险/会议）、责任人、截止日、状态。
- 变更批准时二选一：自动更新基线，或强制触发“重新基线”动作。
- 关口条件、变更遗留项、风险应对统一进行动清单，项目页显示“未关闭行动”。
- 甲方确认做成一条记录（谁、何时、结论、附件），不是一条评论。

### 4. 任务计划模型还不够“能排”（P1）

- 只支持完成-开始（FS），没有 SS/FF/SF。
- 只跳周末，没有法定节假日、公司日历、多日历。
- 任务没有资源分配和成本，只有负责人文本；不能做资源平衡。
- 只有一版基线，不能保留多版；没有 actual start/finish。
- 没有任务约束（不得早于/必须于）、deadline、WBS 模板。
- 不能导入/导出 Excel 或 Microsoft Project XML，和现有 PM 习惯接不上。

**建议**：按使用频率排序，先做“任务分配 + 实际起止 + 节假日日历 + 基线历史”，再做依赖类型和导入导出。不要一上来做资源平衡算法，先把人、任务、日期对上。

### 5. 生产安全与运维（P0）

- 本地账号体系，没有 SSO/LDAP/OIDC，没有 MFA。
- 应用本身不做 HTTPS，靠反代；内网直接开 5177 就是明文。
- CSP 因为内联样式放了 `style-src 'unsafe-inline'`，XSS 防线弱一截。
- SQLite 单文件单写入者，适合小团队；多实例、高并发会撞墙。
- 备份脚本有，但靠手工 cron；没有恢复演练记录、没有备份保留策略。
- 审计日志没有自动保留/归档/导出策略。
- 除登录外没有明显限流；`GET /plan` 还会写库。
- 没有第三方安全测试/渗透测试记录。

**建议**：先做四件事——强制 HTTPS、PMO 账号 MFA、自动备份+季度恢复演练、审计导出与保留。SSO 可以排后面，但这四件不能拖。

### 6. 架构和可维护性（P1/P2）

- `server.js` 约 4000 行，`public/app.js` 约 4600 行，都是单文件；改一个域要全文搜索。
- 只有接口集成测试，没有前端/E2E 测试、没有可访问性自动检查、没有负载测试。
- 没有 CI；迁移靠 `ensureColumn` 逐个补，缺少版本化迁移脚本和回滚说明。
- 没有后台任务队列，报表、通知、快照都只能同步做。
- 单机 SQLite + 同步写，10–50 人没问题，再往上要评估 PostgreSQL。

**建议**：不用现在拆微服务。先把 `server.js` 按 identity / portfolio / plan / reporting / admin 分模块，加一层 migration 目录和 CI，再加 Playwright 跑 5 条关键路径。等并发和多实例真的成为问题时再换库。

### 7. 体验与采纳（P1）

- 12 个一级导航、项目页 8 个页签，信息密度高；新用户第一周需要培训。
- 没有全局搜索、通知中心、收藏/最近访问。
- 周报还是大段文本，项目经理每周重复写；没有“从上周复制/从计划带入”。
- 移动端表格要横向拖，现场更新不方便。
- 没有批量操作（批量审核、批量催办、批量改负责人）。

**建议**：少加页面，多做“少填一次”。周报结构化 + 自动带入 + 移动端快速更新，比再加一个分析页更能提升采纳率。

### 8. 数据与报表（P2）

- 健康度、EVM、进度只有当前值，没有历史快照，画不出趋势。
- 项目群周报能自动生成，但不能批注、版本化、审批。
- 没有收益实现、投资回报、资源产能趋势。
- 指标口径散在代码里，没有指标字典。

**建议**：加 `metric_snapshots`（按周存项目/项目群指标）和 `report_versions`；先做 6 个核心指标的趋势，不要做几十个图。

## 五、建议路线图

### 0–30 天：把“数”变成一套

1. 任务进度 → 项目进度 → 周报/EVM 同源。
2. 周报自动带出本周计划任务，减少重复填报。
3. 把 `computePlan()` 移出 GET，改成写后重算。
4. 补 CI：接口测试 + 5 条 Playwright 关键路径 + axe 可访问性检查。
5. 自动备份 + 恢复演练 + 审计导出。
6. HTTPS 强制、PMO MFA。

### 31–60 天：把“治理”闭上

1. `benefits` 收益台账 + 组合优先级评分。
2. `actions` 行动项：关口条件、变更遗留、风险应对统一跟踪。
3. 甲方验收记录，不是评论。
4. 变更批准后更新基线或强制重新基线。
5. 节假日日历、任务分配、实际起止。
6. 通知中心/催办（先站内，后邮件/IM）。

### 61–90 天：把“组合”做出来

1. 多项目群/组合视图。
2. 收益实现跟踪和投资排序。
3. 指标快照与趋势。
4. Excel / MS Project XML 导入导出。
5. 安全加固与一次渗透测试。
6. 性能压测，确定 SQLite 的实际上限。

## 六、现在不建议做的

- **不要做聊天、文档库、通用工作流引擎。** 这些应该接企业微信/钉钉/SharePoint，不是 PMO 工具的主业。
- **不要追 Microsoft Project 的功能全量。** 资源平衡、任务成本、多日历是另一个产品方向；先把任务、进度、基线、周报打通。
- **不要先做 AI 自动写周报。** 数据不准的时候，AI 只会把错的东西写得更漂亮。
- **不要急着微服务化。** 现在的问题是模块边界和数据一致性，不是部署规模。

## 七、建议盯的指标

不要用“功能数量”衡量这个系统，建议盯：

- 周报按时提交率、PMO 平均审核时长。
- 计划任务进度更新率（有多少任务超过 2 周没更新）。
- 基线偏差（项目群平均、最差项目）。
- 关口一次通过率、关口条件关闭率。
- 变更从提出到结论的周期。
- 高风险关闭率、超期行动项数量。
- 月活用户/周活用户、每人每周填报耗时。
- 备份恢复演练时间、审计异常事件数。

## 八、最终判断

这个系统已经过了“能不能用”的阶段，正在进入“数据可不可信、治理有没有闭环”的阶段。**下一步最值得投入的不是再加一个视图，而是让计划、周报、EVM、关口、变更用同一套数据说话。**

如果只服务一个 PMO 和几十个项目经理，保持现在的单体 + SQLite 是合理的，先把上述 P0 补掉即可；如果要上升到集团多项目群、多组织、多实例，数据库、身份、后台任务和模块边界都要重新设计，不能靠继续加页面解决。
