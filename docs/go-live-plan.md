# PMO 项目群管理台正式上线实施建议

日期：2026-11-03  
对应版本：v1.38.0  
定位：一个 PMO、2–3 个项目、10–20 名用户的内部试点，验证后再逐步扩到全项目群。

## 一、结论

**不建议直接全量正式上线，建议先做 2 周小范围试点，再分批推广。**

现在的系统功能已经够用：计划、周报、EVM、关口、收益、验收、供应商、模板、日历、资源、多项目群、帮助和 AI 都有，40 项接口测试、浏览器冒烟、安全基线和压测也都能跑。但它仍然是**单 Node 进程 + SQLite 单文件**，没有内置 SSO/MFA/TLS，也没有正式监控和自动备份。功能之外，正式上线真正缺的是运维和身份这两块。

建议的上线路径：

1. **准备期（1–2 周）**：补 TLS、备份、监控、账号清理、数据初始化、培训和回滚预案。
2. **试点期（2 周）**：2–3 个项目、10–20 人，PMO 全程跟。
3. **推广期（第 3–6 周）**：按部门或项目群分批开，不一次全开。
4. **稳定期（第 7–12 周）**：看数据、看采纳、再决定是否上多实例或换 PostgreSQL。

## 二、当前就绪度

| 项目 | 现状 | 正式上线判断 |
| --- | --- | --- |

## 三、上线前必须补齐（P0）

下面这些没做完，建议只做试点，不要宣布正式上线。

| # | 事项 | 验收证据 | 建议负责人 |
| --- | --- | --- | --- |
| 1 | HTTPS 和反向代理 | 浏览器锁标；HTTP 自动跳 HTTPS；`Set-Cookie` 带 Secure；响应带 HSTS | IT 运维 |
| 2 | 访问边界 | 要么接 SSO/MFA，要么只允许 VPN/办公网 IP；公网不直接暴露 5177 | 安全/IT |

| 4 | 自动备份 | 每天至少一次；备份到另一台机器或对象存储；保留 30/90 天；加密 | IT 运维 |
| 5 | 恢复演练 | 从备份恢复到临时环境，登录、看项目、提交周报都正常；记录耗时 | IT 运维 |
| 6 | 监控告警 | 每 5 分钟探活 `/api/health`；进程、磁盘、备份、错误日志有告警；有人收 | IT 运维 |
| 7 | 回滚预案 | 上一版包、数据库备份、回滚步骤、谁拍板，都写下来并演练一次 | 平台负责人 |
| 8 | 安全测试 | 至少做一次漏洞扫描或第三方渗透；高危/中危有处理结论 | 安全 |
| 9 | 生产数据初始化 | 独立生产库；清掉演示项目/账号；项目群、项目、人员、供应商、模板、日历、计划基线都建好 | PMO/数据负责人 |
| 10 | 培训与支持 | PMO 和项目经理各一场培训；帮助中心可访问；有支持群和响应时限 | PMO |
| 11 | AI 边界 | 默认关闭；要用就选内网模型或合规外部模型；写明数据会发给谁；生成内容必须人工复核 | PMO/安全 |
| 12 | 真实数据压测 | 用接近真实项目数、任务数、周报数跑一遍；看 p95、SQLite 锁、磁盘增长 | IT/开发 |

### 3.1 生产库不要直接用演示库

建议单独指定：

```bash
PMO_DB=/opt/pmo/data/pmo.db
```

第一次启动会自动写演示数据。正式初始化顺序：

1. 启动后先用 PMO 登录。
2. 管理维护 →「清空业务数据」（保留当前管理员和默认项目群）。
3. 新建真实项目群、项目、账号。
4. 配供应商、模板、工作日历。
5. 用 CSV/XML 导入或手工建整体计划，设基线。
6. 核对项目数、账号数、计划任务数，再让用户登录。

**不要在生产库点“重置演示数据”**，那会把演示项目重新灌回来。

### 3.2 备份建议

- 用 `npm run backup` 或 SQLite 的 `.backup`，不要在写入过程中直接 `cp` 单文件。
- 备份文件放另一台机器或对象存储，不要和数据库同盘。
- 至少保留最近 30 天日备、12 个月月备。
- 每季度做一次恢复演练，记录 RPO/RTO。
- 建议目标：RPO ≤ 24 小时，RTO ≤ 2 小时。

### 3.3 账号与权限

- PMO 账号控制在 2–3 个，避免人人都是管理员。
- 乙方项目经理只给负责项目；甲方项目经理只读。
- 离职/换项目当天停用账号，不要只改项目负责人。
- 审计日志至少保留 6–12 个月，按季度导出一次。

## 四、上线前的数据准备

### 4.1 必须建好的基础数据

- 项目群：名称、负责人、目标、起止时间。
- 项目：编号、名称、阶段、优先级、预算、计划窗口、甲乙双方项目经理。
- 人员：PMO、乙方项目经理、甲方项目经理；乙方账号挂供应商。
- 供应商：编码、名称、联系人、状态。
- 模板：至少一套周报、计划、里程碑模板，设默认。
- 工作日历：法定假日、调休上班。
- 整体计划：WBS、工期、前置关系、负责人；确认后排一版基线。
- 关口：立项/阶段/验收关口及计划日期；检查清单生成。
- 收益和行动项：至少把当前季度重点项目的收益指标、责任人和时间填上。

### 4.2 数据质量底线

- 项目进度不能靠手填，必须有任务计划；没有计划的项目会被当成手工进度。
- 周报当前周/未来周进度会被计划锁定，先保证计划任务有人更新。
- 关口必检项没完成不能判通过，提前把清单发给项目组准备。
- 收益当前值要有人定期更新，否则只是登记表。

## 五、上线日操作单

### T-1 天

- 冻结代码和配置，确认上一版包和数据库备份可用。
- 再跑一次恢复演练和关键页面冒烟。
- 通知用户上线窗口、支持人和回滚可能。

### T 日

1. 停应用，做一次完整备份。
2. 部署新包，启动服务，检查 `/api/health`。
3. 用 PMO 登录，检查项目列表、计划、周报、帮助、AI 配置状态。
4. 用一个测试项目走一遍：建任务 → 提交周报 → PMO 审核 → 看报表。
5. 开放用户，发上线通知和使用入口。
6. 前 2 小时盯错误日志、登录失败、500、磁盘和备份任务。

### 回滚触发条件

出现下面任一情况，先回滚再排查：

- 登录不可用超过 5 分钟。
- 关键页面持续 500，或错误率明显升高。
- 数据出现错乱、丢记录。
- 安全事件或越权访问。
- 备份任务失败且短时间修不好。

回滚步骤：停服务 → 恢复上一版数据库备份 → 切回上一版包 → 启动 → 验证登录和项目页 → 通知用户。

## 六、上线后 1/7/30/60/90 天

### 第 1 天

- 每小时看一次健康、错误日志、登录失败。
- 收集用户报错，能当场解决的当场解决，解决不了的记录。
- 确认当晚备份成功。

### 第 1 周

- 每天 15 分钟站会：昨天谁卡住、数据有没有明显不对、周报提交率。
- 周五做一次小复盘：哪些页面不会用、哪些字段多余、哪些流程绕。
- 不急着加功能，先修阻断使用的问题。

### 第 7 天

- 看本周周报按时提交率、PMO 审核时长。
- 抽查 2 个项目：计划任务进度是否真实、关口清单是否有人填。
- 根据反馈改帮助文章和模板，不改核心流程。

### 第 30 天（试点退出评审）

建议用下面几条决定是否推广：

- 试点项目周报按时提交率 ≥ 90%。
- PMO 审核 48 小时内完成率 ≥ 90%。
- 计划任务两周内更新过的比例 ≥ 80%。
- 关口通过前检查清单完成率 100%。
- 没有 P0/P1 级数据错误或安全事件。
- 用户愿意继续用，而不是回到 Excel/邮件。

达到就扩到下一批项目；达不到先解决采纳和数据质量问题，不要硬推。

### 第 60 天

- 看组合优先级、收益达成、资源超载是否真的被用于例会。
- 看变更、验收、行动项有没有形成固定节奏。
- 评审 AI 使用：用了多少次、多少是本地降级、有没有出现明显错误。
- 做一次备份恢复演练和安全复查。

### 第 90 天

- 决定是否继续扩大项目群/部门。
- 评估 SQLite 是否还撑得住：并发写入、数据库大小、p95、备份窗口。
- 排下一阶段：按项目群拆分指标快照、SSO/MFA、移动端、资源平衡、正式 E2E。

## 七、角色与支持

| 角色 | 负责什么 |
| --- | --- |
| 业务负责人（PMO） | 流程、模板、关口、数据口径、试点验收 |
| 平台负责人（IT） | 部署、TLS、备份、监控、升级、回滚 |
| 安全 | 访问边界、账号策略、漏洞/渗透、AI 数据合规 |
| 数据负责人 | 项目、人员、供应商、计划、基线初始化 |
| 培训/支持 | 培训、帮助中心、问题收集、一线答疑 |
| AI 负责人（如启用） | 模型选型、密钥、成本、隐私、输出抽查 |

支持建议分两级：一线 PMO 管理员处理账号、模板、填报问题；IT 处理服务、网络、备份、性能。设一个支持群，明确响应时间，例如工作时间 2 小时内响应。

| 指标 | 建议目标 |
| --- | --- |
| 工作时间可用性 | ≥ 99.5% |
| 真实数据下接口 p95 | < 500ms |
| 每日备份成功率 | 100% |
| 恢复演练 | 每季度一次，RTO ≤ 2 小时 |
| 周报按时提交率 | ≥ 95% |
| PMO 48 小时内审核率 | ≥ 90% |
| 计划任务两周内更新率 | ≥ 80% |
| 关口通过前清单完成率 | 100% |
| 周活用户/应使用用户 | ≥ 80% |
| AI 生成内容人工复核 | 100%（流程要求） |

## 九、主要风险

| 风险 | 说明 | 处理 |
| --- | --- | --- |
| SQLite 单写入者 | 多人同时写可能锁等待；单机故障影响大 | 单实例部署、WAL、自动备份；用户/写入量上来再评估 PostgreSQL |
| 数据丢失 | 单文件、磁盘故障、误操作 | 异机备份、恢复演练、生产库禁止 reset |
| 越权/账号共用 | 本地账号、无 MFA | 网络限制或 SSO/MFA、一人一号、离职即停 |
| AI 数据外发 | 项目内容发给外部模型 | 默认关闭；优先内网模型；敏感项目不启用 |
| 采纳不足 | 用户回到 Excel | 培训、模板、周报自动带入、试点 champion |
| 过度定制 | 每个部门加字段/流程 | 上线前冻结范围，变更走评审 |
| 单机性能 | 数据量增长后变慢 | 监控 p95、磁盘、锁等待；定迁移阈值 |

### PostgreSQL 迁移阈值

不用现在迁。出现下面任意两条再评估：

- 并发写入经常锁等待，影响使用。
- 数据库文件超过 2GB，备份窗口明显变长。
- 需要多实例/高可用。
- 用户超过 100 人，或接口 p95 持续超过 500ms。
- 需要跨系统实时集成/报表抽取。

## 十、AI 上线建议

建议分三步：

1. **先关闭**：默认 `PMO_LLM_BASE_URL` 不配置，帮助问答用知识库检索，项目 AI 用本地规则摘要。
2. **内网模型试点**：选 Ollama/vLLM 等内网 OpenAI 兼容服务，只开给 PMO 和 2–3 个项目；抽查 20 个真实问题的回答。
3. **再评估外部模型**：只有确认数据分级允许，才配外部 API；密钥只放服务端，设置成本上限，生成内容必须人工复核。

三条底线：

- 不把账号、密码、密钥、合同金额等敏感信息贴进提问框。
- 不让 AI 直接写周报/改计划，只做草稿。
- 每周抽查 AI 输出，出现明显错误就收紧使用范围。

## 十一、Go / No-Go 判断

**可以试点（Conditional Go）**：

- TLS、备份、恢复演练、监控、管理员账号、回滚预案都完成。
- 数据清空并完成初始化。
- 培训和帮助中心就绪。
- 只开 2–3 个项目、10–20 人。

**可以正式推广（Go）**：

- 试点 30 天指标达标。
- 没有 P0/P1 数据或安全事件。
- 有明确支持人和值班安排。
- 第三方渗透或漏洞扫描完成，高危已处理。

**不允许上线（No-Go）**：

- 没有可用备份或没做过恢复。
- 生产库还夹着演示数据/演示账号。
- 公网直接暴露 5177，或管理员账号共用。
- 没有回滚包和回滚步骤。
- AI 外部模型未经数据合规确认就处理敏感项目。

## 十二、建议的下一步（7 天内）

1. 定生产环境：独立 `PMO_DB`、systemd、Nginx、TLS、VPN/办公网访问。
2. 配自动备份到异机，做一次恢复演练并记录时间。
3. 清空生产库演示数据，建 1 个项目群、2–3 个试点项目、真实账号。
4. 配供应商、模板、工作日历，导入计划并设基线。
5. 做 PMO 和项目经理两场培训，发帮助中心入口。
6. 定支持群、响应时限、回滚拍板人。
7. 开始两周试点，按第 7/30 天节点复盘，再决定推广。
